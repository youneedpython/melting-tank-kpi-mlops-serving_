# v4 Git 브랜치 전략

## 목적

v3 태그가 가리키는 안정 버전을 보존하면서 AWS 인프라와 CI/CD를 여러 단계로 구현합니다. 수업에서는 기능별 브랜치와 Pull Request를 통해 코드 검증과 배포 승인을 구분합니다.

## 브랜치 역할

| 브랜치 | 역할 | 직접 Push |
|---|---|---|
| `main` | 배포 가능한 안정 버전과 태그 | 금지 권장 |
| `develop` | v4 기능 통합 및 전체 검증 | 금지 권장 |
| `feature/v4-aws-infra` | CloudFormation, S3, ECR, ECS, ALB | 허용 |
| `feature/v4-github-actions` | CI·CD 워크플로 및 문서 | 허용 |

## 진행 순서

```bash
git switch main
git pull origin main
git switch -c develop
git push -u origin develop

git switch -c feature/v4-aws-infra
# 인프라 파일 작업·검증·커밋·Push 후 develop 대상 PR

git switch develop
git pull origin develop
git switch -c feature/v4-github-actions
# Actions 파일 작업·검증·커밋·Push 후 develop 대상 PR
```

`develop` 통합 테스트가 끝난 뒤 `develop → main` Pull Request를 병합합니다. AWS 배포와 readiness까지 확인한 후 태그를 생성합니다.

```bash
git switch main
git pull origin main
git tag -a v4.0.0 -m "release: AWS ECS CI/CD 배포 파이프라인 v4.0.0"
git push origin v4.0.0
```

태그 Push는 CD를 실행하므로, 승인 모델이 S3에 있고 ECS 서비스가 정상 구성된 뒤 수행해야 합니다.

## 권장 보호 규칙

- `main`: Pull Request 필수, CI 성공 필수, force push 금지
- `develop`: Pull Request 필수, CI 성공 필수
- GitHub `production` Environment: 배포 승인자 지정
- AWS 장기 Access Key를 Secrets에 저장하지 않고 OIDC 역할 사용
